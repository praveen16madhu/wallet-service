Lesson 1: idempotency

The user taps "Pay" twice

The phone times out, so the app sends the same deposit again. Without protection the money is added twice. With an Idempotency-Key the server recognises the repeat and replays the first answer.

Lesson 2: transactions

The server crashes halfway through a transfer

A transfer is two steps: take from A, give to B. If the app dies in between, money would vanish. Both steps run in one database transaction, so a crash undoes the debit.

Lesson 3: locking

Twenty withdrawals at the same instant

Each request reads the balance, subtracts, and writes it back. If two read the same number, one subtraction is lost. With locking (SELECT ... FOR UPDATE) requests queue up one at a time and the numbers add up.

Lesson 4: timeouts and retries

The notification service is slow, flaky, or dead

The wallet calls another service with a 1 second connect timeout and a 1.5 second read timeout, and retries up to 3 times. "Dead" is refused instantly (nobody is listening). "Slow" connects but never answers in time, so the read timeout fires.

Lesson 5: Kafka

Events: duplicates and bad messages

After a transfer commits, an event goes to Kafka. The consumer stores it with the transfer id as primary key, so a redelivered event is ignored. A malformed event goes to a dead-letter topic instead of blocking the queue. These are verified by the automated tests using an embedded broker.

Kafka is off by default (no broker is installed). To use it, start a broker and run with WALLET_KAFKA_ENABLED=true.
